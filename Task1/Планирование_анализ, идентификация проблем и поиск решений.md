# Проблемы (фактические и потенциальные)

1. Отсутствие масштабирования

* По одному инстансу каждого сервиса и каждой БД → ограничение пропускной способности, риски простоя.
* RabbitMQ, судя по описанию, также одиночный → риски потери/задержки сообщений.

2. Долгий и неуправляемый расчёт цены в MES

* 2–3 мин в среднем, до 30 мин на сложных моделях.
* С высокой вероятностью расчёт делается синхронно в веб-процессе MES API/воркера без чёткой системы очередей/пулов → блокировки потоков, «прожигание» ресурса под всплесками.
* Нет уровней QoS, backpressure, таймаутов, кэша.

3. Узкое горлышко и потеря событий в интеграциях

* Заказ в CRM создаётся «через сообщение из очереди от MES». При задержках/повторной доставке/ошибках подтверждений CRM не видит заказ → «не получили заказ».
* Нет гарантированной доставки/дедупликации, механизмов повторной подачи.

4. Резкий рост входящего трафика через открытый API

* Нет (или недостаточно) лимитов.
* Высокая доля «расчётов ради прицениться» съедает вычислительный бюджет и забивает очередь реальным заказам.

5. Медленная главная страница MES для операторов

* Даже с пагинацией и фильтрами тормозит → вероятны тяжёлые запросы (джоины по многим статусам), отсутствие индексов/материализованных представлений.
* Бизнес-эффект: операторы обновляют страницу ради самых новых заказов (мотивация «кто успел — того и деньги») → DDoS-подобная нагрузка.

6. Размытый источник истины по статусам

* Изменения статусов происходят в разных системах (онлайн-магазин, MES, CRM). Без саг/оркестрации и outbox-паттерна статусы рассинхронизируются, заказы застревают.

7. Ручная обработка статусов «MANUFACTURING\APPROVED»

* Ручное «бутылочное горлышко» в CRM, нет SLA/авто-правил  → накапливается очередь.

8. Слабая наблюдаемость

* Нет end-to-end трассировки, дашбордов по длинам очередей, p95 времени расчёта/доставки событий, зстрявших заказов и т. п. → проблемы видимы только глазами клиентов.

9. Процессы релизов

* Ручной деплой в release/prod → задержки фиксов в проде при растущей нагрузке.
* Мало автотестов (особенно контрактов между сервисами и нагрузочных).


10. 3D-файлы

* Нет нормирования сложности (полигоны/размер), отсутствует предварительная декомпозиция/снижение сложности для оценки → слишком сложные модели блокируют расчёт.

11. Коммуникация с B2B-партнёрами

* Нет подтверждённых webhook’ов/уведомлений/портала статусов; партнёры не получают заказ и не понимают, где он.

# Инициативы (что делаем)

A. Усиление событийного контура и надёжной доставки

* Разделить обмен на «команды» и «доменные события», ввести outbox-паттерн в Shop API, CRM API, MES API.
* Включить идемпотентность на приёме, дедупликацию и ретраи с экспоненциальной паузой.
* Разнести очереди/экченджи по типам нагрузок (ценообразование, статусы, заказы).
* Поднять RabbitMQ в HA-кластере.

B. Выделение Pricing Service + пул воркеров

* Вынести расчёт стоимости из MES API в отдельный сервис c очередью задач, горизонтальным масштабированием воркеров.
* Ввести асинхронный контракт: 202 Accepted + jobId, получение результата по webhook.
* Кэширование результатов на идентичные модели.

C. Витрина данных (CQRS) для главной страницы MES

* Отдельная read-модель (Redis/Elastic/материализованные представления Postgres).
* WebSocket/WebPush уведомления о новых заказах без обновления страницы.
* Ввести резервацию заказа на X минут при открытии карточки (или автораспределение) для справедливости и снижения гонки.


D. Контроль входящего трафика открытого API

* Rate limiting, ключи партнёров, приоритеты.
* Разделить /quotes (котировка) и /orders (оформление), TTL котировки.
* Документация и sandbox, versioning API, webhooks для статусов.

E. Наблюдаемость и SLO

* OpenTelemetry трассировка между Shop/CRM/MES/RabbitMQ.
* SLO: p95 рассчёта цены, p95 времени создания заказа в CRM после SUBMITTED, p95 времени смены статуса.
* Дашборды: длина очередей, время в очереди, rate ошибок, «зависшие» заказы, отставание проекций.

F. БД и производительность

* Реплики на чтение для Shop/MES/CRM, pgbouncer.
* Индексы: (status, createdAt), покрывающие по основным спискам.
* План запросов главной страницы MES, устранение N+1, материализованные представления по «заказам в работе».

G. CI/CD и качество

* Полностью автоматический деплой в staging/release, канареечный/blue-green в prod.
* Контрактные тесты (CDC) между сервисами и для внешнего API.
* Нагрузочные тесты: Pricing, CRM-создание заказа, MES-дашборд.
* Минимальный прод-смоук после релиза, быстрая обратная связь.


# Приоритеты (почему в таком порядке)

1. A. Событийный контур + HA RabbitMQ — устранение корня жалоб «не получили заказ», убираем потери/задержки/дубликаты, создаём базу для всего остального.
2. B. Pricing Service — главный потребитель CPU и источник бэкпрешура. Делаем управляемым, масштабируемым и асинхронным.
3. C. Витрина для MES (CQRS) + резервация/автораспределение — снимает постоянный боль операторов и паразитную нагрузку.

Эти три мероприятия дают максимальный эффект на бизнес-метрики: меньше потерянных/застрявших заказов, выше скорость обработки, ниже нагрузка пиков, лучше опыт операторов и партнёров. Остальные инициативы (оркестратор, CI/CD, наблюдаемость, оптимизация БД) — логичные следующие шаги, и их проще внедрять уже на устойчивом фундаменте.

# Целевая архитектура через 6 месяцев

* Горизонтально масштабируемые экземпляры Internet Shop/Shop API, CRM/CRM API, MES FE и MES API за балансировщиком. Сессии вне процесса (Redis).
* Pricing Service как отдельный доменный сервис с очередью задач и пулом воркеров; 202 + jobId; webhooks; кэш; лимиты/нормализация 3D.
* RabbitMQ HA-кластер, разделённые обменники по доменам; outbox во всех сервисах; идемпотентные потребители.
* Order Orchestrator хранит состояние саги заказа; CRM/MES/Shop подписчики событий.
* CQRS-витрины: Redis/Elastic/материализованные представления для быстрых списков (операторский инбокс, «новые заказы»).
* Наблюдаемость: OpenTelemetry трассировка, SLO дашборды, алерты по очередям/временам/ошибкам.
* БД: реплики на чтение, индексы под ключевые запросы.
* CI/CD: канареечные релизы в prod, автотесты (unit/integration/CDC/load), быстрый смоук, фича-флаги.
* API для партнёров: rate limits/quotas, разделение quotes vs orders, webhooks/портал статусов.

Ожидаемые метрики:

* p95 получения котировки: ≤5 мин (при «тяжёлых» моделях), среднее ≤2 мин; отказ в лоб — мгновенно (валидаторы).
* p95 создания заказа в CRM после SUBMITTED: ≤30 сек.
* Доля «застрявших» заказов → \~0; потери/дубликаты событий → \~0.
