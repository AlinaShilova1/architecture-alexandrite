# Мотивация

Сейчас основная боль бизнеса и команды — потерянные и зависшие заказы. Проблема усугубляется тем, что нет прозрачности между системами:

* Онлайн-магазин фиксирует SUBMITTED,
* MES считает цену,
* CRM подтверждает заказ,
* сообщения бегают через RabbitMQ,
* часть заказов уходит в B2B API,
* но никто не видит полную цепочку.

### Что даёт трейсинг

1. Прозрачность процесса

    * Видим путь заказа от момента создания до отправки клиенту в единой ленте.
    * Можно быстро ответить бизнесу и клиентам: «На каком этапе заказ» и «почему он задержался».

2. Ускорение поиска багов

    * Сейчас разработчики вручную ищут логи в разных сервисах → это занимает часы.
    * С трассировкой время расследования инцидентов сократится с нескольких часов до минут.

3. Предотвращение потерь сообщений

    * RabbitMQ — центральная шина, но без контроля потерянные/дублированные события не видны.
    * Трассировка событий и DLQ в единой системе позволит найти и автоматически переправить такие сообщения.

4. Фокус на SLA

    * Впервые появятся реальные метрики по SLA на каждый этап: время расчёта цены, время до начала производства, среднее время в очереди.
    * Можно установить целевые KPI и объективно контролировать их выполнение.

5. Фундамент для автоматизации и улучшений

    * На базе трассировки можно строить автоматические алерты, дашборды, аналитику по узким местам.

---

### Метрики, на которые повлияет внедрение

Технические:

1. Время обработки заказа на каждом этапе (SUBMITTED → PRICE\_CALCULATED → MANUFACTURING\_STARTED → SHIPPED → CLOSED).
2. Количество потерянных сообщений и повторных попыток доставки.
3. RabbitMQ lag — возраст самого старого сообщения.
4. Количество заказов, зависших более чем на SLA в конкретном статусе.
5. p95 и p99 времени расчёта стоимости изделия (Pricing Service).

Бизнес:

1. % заказов, завершённых вовремя.
2. Количество жалоб «не получили заказ» или «заказ завис».
3. Среднее время от создания заказа до начала производства (lead time).
4. Скорость восстановления после инцидентов (MTTR).
5. % успешно обработанных заказов через B2B API без ручного вмешательства.

# Где может сломаться заказ

Ниже — ключевые места, где заказ может зависнуть или потеряться. Эти точки должны быть покрыты трейсингом:

| Этап                              | Потенциальная проблема                                                     | Где фиксировать спан            |
| --------------------------------- | -------------------------------------------------------------------------- | ------------------------------- |
| 1. Создание заказа (Shop API) | Пользователь отправил заказ, но он не ушёл в RabbitMQ или ушёл дважды      | Shop API → outbox event         |
| 2. RabbitMQ                   | Сообщение потеряно, застряло, нет подтверждения, DLQ растёт                | RabbitMQ consumer и producer    |
| 3. MES (Pricing)              | Расчёт завис, воркер умер, сложная модель блокирует очередь                | MES API и воркер Pricing        |
| 4. CRM                        | Заказ не создался после обработки события из MES, либо статус не обновился | CRM API при обработке сообщений |
| 5. B2B API                    | Партнёр не получил callback или мы не сохранили входящие данные            | Shop API (B2B endpoint)         |
| 6. MES дашборд                | Статус виден оператору с задержкой или не обновляется                      | MES API при отдаче данных       |
| 7. Завершение заказа          | Нет перехода в CLOSED из-за ошибок логистики или потерянного сообщения     | CRM API при завершении          |

# Какие данные собирать в трейсинг

Для каждого спана (span) должны попадать следующие данные:

| Категория                 | Данные                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------- |
| Идентификатор         | trace_id — единый для всего заказа, span_id — уникальный для шага                 |
| Заказ                 | order_id, source (b2c, b2b), partner_id (если B2B), sku_type (custom/catalog) |
| Сервис                | service_name, environment, version                                              |
| RabbitMQ              | queue_name, message_id, retry_count                                             |
| MES                   | model_hash, polygon_count, job_id                                               |
| CRM                   | crm_user_id (кто подтвердил заказ), status                                        |
| B2B API               | client_id, callback_url                                                           |
| Тайминги              | start\_time, end\_time, duration                                                      |
| Результат             | success/failure, код ошибки                                                           |
| Техническое окружение | host, pod/container id                                                                |

Дополнительно:

* В случае ошибок — текст ошибки + stack trace.
* Корреляция с логами через trace_id и span_id.

# Предлагаемое решение

### Инструменты

* OpenTelemetry — единый стандарт для метрик, логов и трассировок.
* Jaeger (или Tempo в Grafana Cloud) — хранилище и визуализация трейсинга.
* OTel SDK:

    * Java (Shop API, CRM API),
    * .NET (MES API),
    * JS (фронтенд MES и Shop),
    * C# воркеры Pricing.
* RabbitMQ instrumentation — отдельный плагин для фиксации событий отправки/чтения сообщений.
* Trace ID генерация в Shop API: При создании заказа формируется trace_id, который прокидывается через все заголовки (X-Trace-ID) и в сообщения RabbitMQ.

### Поток данных

1. Shop API генерирует trace_id при SUBMITTED.
2. trace_id идёт:

    * в HTTP-заголовках → CRM, MES,
    * в RabbitMQ → как часть payload или заголовка сообщения.
3. Каждый сервис при обработке:

    * создает span (например, «pricing\_calculation»),
    * передаёт trace_id и parent_span_id дальше.
4. Воркер Pricing создаёт отдельные спаны для:

    * «start pricing»,
    * «processing file»,
    * «saving result».
5. В Jaeger/Grafana можно увидеть:

    * дерево спанов по заказу,
    * где задержка или ошибка,
    * время на каждом этапе.

---

### Новые компоненты на схеме

Добавляем:

* Tracing Collector (OTel Collector) — красный блок, получает данные от всех сервисов.
* Tracing Storage (Jaeger/Tempo) — красный блок, хранит трейсинг.
* Новая стрелка «Trace Data» от всех сервисов → OTel Collector → Jaeger.

# Компромиссы

1. MES — проприетарный код

    * Трассировка воркеров на C# потребует доработок, пока это не автоматизировано.
    * Компромисс: начнем с верхнего уровня (MES API), а воркеры подключим позже.

2. B2B партнёры

    * Мы не можем заставить партнёров прокидывать trace_id во все свои запросы.
    * Решение: для B2B создаём наш trace_id при входящем запросе.

3. Стоимость хранения

    * Полные трейсинги по всем заказам дороги.
    * Tail-based sampling:

        * 100% выборка ошибок и медленных трейсингов,
        * 10% нормальных заказов.

4. Фронтенд MES и Shop

    * JavaScript трейсинг менее точный и сложнее масштабируется.
    * На старте собираем только ключевые пользовательские действия (создание заказа, открытие дашборда).

# Безопасность

1. Аутентификация и роли

    * Доступ в Jaeger только через корпоративную SSO/LDAP.
    * Роль «Поддержка» — просмотр трейсингов, роль «Администратор» — настройка.

2. Фильтрация данных

* Не хранить в трейсингах персональные данные (ФИО, адрес, телефон).
    * Для идентификации использовать только order_id и partner_id.

3. Шифрование

    * Все трассы передаются в Collector по TLS.
    * Хранение данных в зашифрованном виде.

4. Retention

    * Хранение детальных трейсингов: 7 дней.
    * Агрегированных данных: 30 дней.

# Результат после внедрения

* Команда сможет за 1-2 минуты найти, где застрял заказ.
* RabbitMQ DLQ и ретраи будут прозрачно видны в Jaeger.
* Бизнес сможет видеть:

    * среднее время каждого этапа,
    * количество зависших заказов,
    * количество потерянных сообщений.
* Пользователи получат более точные сроки выполнения и меньше жалоб.
