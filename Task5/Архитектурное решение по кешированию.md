# Мотивация

MES тормозит в двух больных местах:

* Список заказов на главной (операторский инбокс): тяжёлые запросы, частые F5, потребность «видеть новые заказы первее всех».
* Долгая котировка/оценка (pricing): повторные расчёты одних и тех же (или очень похожих) моделей.

Кеширование решает:

* Быструю отдачу «ленты» заказов при скролле и переключении статусов.
* Снижение нагрузки на БД MES.
* Мгновенную видимость свежих заказов без постоянных refetch.
* Устранение повторных расчётов цены для идентичных входных данных (B2B/B2C).

Область применения кеша:

1. MES список заказов (по статусу/дате) — горячее чтение.
2. MES детали заказа (карточка) — средняя горячесть, много повторов.
3. Pricing результаты (по model_hash + параметрам) — высокий выигрыш от повторного использования.

# Предлагаемое решение

## Тип кеширования

* Серверное кеширование — основа (Redis/KeyDB).
  Причины: контролируемая согласованность, единая политика инвалидации, независимость от браузера, кросс-канальность (B2B, операторы, админы).
* Клиентское кеширование (дополнительно) — ETag/Last-Modified + короткие max-age для статичных ресурсов, stale-while-revalidate для списка (через SW/FETCH политики). Это снижает перезапросы при навигации и восстановлении вкладок, но не решает серверную нагрузку в одиночку.

## Паттерны

* Cache-Aside (основа) для: списка заказов, деталей заказа, результатов pricing.
  Почему: даёт простую деградацию (кеш недоступен → читаем БД), удобную точечную инвалидацию по ключам, хорошо ложится на Redis.
* Refresh-Ahead (выборочно) для «горячих» ключей списка (orders:list:{status} первых страниц): фоновые обновления предотвращают TTL-шторма, операторы почти всегда получают тёплый кеш.
* Write-Through — не используем для заказов: записи редки, логика статусов — транзакционная, безопаснее записать в БД, а кеш инвалировать/обновлять асинхронно.

## Ключи кеша и TTL

* Список заказов (keyset-пагинация):
  orders:list:{status}:{cursor|page}:{filters_hash} → JSON (идшники, краткие поля).
  TTL: 10–30 секунд + refresh-ahead для первых N страниц.
* Детали заказа:
  orders:detail:{order_id} → JSON. TTL: 1–5 минут; принудительная инвалидация по событию изменения.
* Pricing результат:
  pricing:quote:{model_hash}:{params_hash} → результат/стоимость. TTL: 7–30 дней; ручная инвалидация если пересчитали движок/материалы.

## Инвалидация

Комбинированная стратегия:

1. Программная (event-driven) — основная.
   После изменения статуса в MES: публикуем событие OrderStatusChanged(orderId, old, new, ts) в шину → инвалидируем:

    * orders:detail:{orderId}
    * соответствующие ключи списков, куда заказ входит/из них уходит (например, из PRICE_CALCULATED в MANUFACTURING_APPROVED).
      Широкая инвалидация ускоряется tag-like префиксами: храним набор ключей для orders:list:{status} (Redis Set) и чистим их батчем.
2. Временная (TTL) — защита от застоя и сетевых глитчей (10–30 с на списки, 1–5 мин на детали).
3. Refresh-Ahead — для «первых страниц» популярных статусов обновляем кэш до истечения TTL.
4. По ключу — для pricing при деплое новой версии оценщика: инкрементируем версию пространства ключей (pricing:v2:...), старое пространство естественно устаревает без массового DEL.

Почему не «только TTL»: изменённый статус должен отражаться сразу, TTL может дать «фантомные» данные. Почему не «только программная»: без TTL редкие пути могут «забыться» при сбоях событий.

## Точки интеграции

* MES API: оборачивает DAO чтения через Cache-Aside; пишет в БД, после коммита шлёт событие → инвалидация.
* CQRS Read-модель (рекомендуется): материализованные списки «заказы по статусу по дате» в отдельной read-БД/индексе (Postgres MV/Elastic). Кеш кладём поверх read-модели — ещё быстрее и дешевле.
* Pricing Service: после успешного расчёта кладёт результат в кэш; при запросе сначала ищем по model_hash.

## Прикладные детали реализации

* Redis: кластер/репликация, эвикция allkeys-lru, ограничение памяти, мониторинг hit-rate.
* Keyset-пагинация: WHERE status = ? AND (created_at,id) < (?,?) ORDER BY created_at DESC, id DESC LIMIT ?.
* Наборы ключей: orders:list:index:{status} — Redis Set со всеми актуальными ключами списков; при инвалидации делаем SMEMBERS + pipeline DEL/UNLINK.
* Refresh-Ahead: фоновые воркеры обновляют 1–3 «первых страниц» по «топ-статусам» (задаётся конфигом).
* Pricing hash: SHA256(file_content_norm) + params (нормируем 3D перед хешем: единицы, порядок, отбрасываем незначащие атрибуты).

## Сравнение подходов (кратко)

| Вариант                               | Плюсы                                     | Минусы                                                      | Где применяем                             |
| ------------------------------------- | ----------------------------------------- | ----------------------------------------------------------- | ----------------------------------------- |
| Только клиентский кеш (ETag/HTTP) | Простота, меньше запросов                 | Не разгружает БД при кэше-мисс, слабый контроль инвалидации | Используем как дополнение (FE)            |
| Серверный Cache-Aside             | Прозрачная деградация, гибкая инвалидация | Нужно кодировать путь miss→DB→set                           | Основной паттерн                          |
| Write-Through                     | Кеш всегда актуален                       | Каждая запись дороже, риск двойной записи                   | Не используем для заказов                 |
| Refresh-Ahead                     | Нет TTL-штормов, быстрые хиты             | Нужна эвристика «горячих» ключей                            | Для первых страниц списков                |
| Только TTL                        | Простота                                  | Неконсистентность при смене статуса                         | Только как защита + совместно с событиями |

## Ожидаемые эффекты (SLO/метрики)

* TTFB главной страницы MES: ≤ 200–300 мс (p95).
* Снижение запросов к БД на списке: в 5–15 раз.
* Доля кэш-хитов списка: ≥ 80% на первых двух страницах.
* Повторные котировки: минус 70–90% за счёт pricing:quote кеша.

## Риски и меры

* Несогласованность при сбоях событий → комбинируем программную инвалидацию и TTL.
* Высокая кардинальность ключей → нормализуем фильтры и ограничиваем вариативность.
* «Тяжёлые» miss-штормы → refresh-ahead + прогрев при релизе.
* Дедлоки на массовой инвалидации → UNLINK/pipeline, инвалидация по префиксам в пачках.
