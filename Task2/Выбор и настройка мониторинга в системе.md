# Мотивация

* B2B-канал через API «съел» картину Я.Метрики. Теперь значимая доля трафика и заказов идет мимо фронта. Нужны технические и продуктовые метрики на бэкендах и в очередях, а не только на витрине.
* Жалобы «заказы потерялись/зависли». Без метрик по очередям, ретраям и сквозной трассировки мы не видим корень проблем и не можем SLA/SLO ни обещать, ни защищать.
* Пиковая нагрузка на Pricing. Время расчёта (до 30 мин) и объём 3D-файлов — критический риск. Нужны метрики, чтобы защищаться rate-limit’ами и масштабированием.
* Медленный дашборд MES. Нужны показатели БД/запросов/кэшей/страниц, чтобы целенаправленно ускорить.
* Бизнес-эффект: меньше просрочек и оттока, возврат крупных контрактов, разумные вместимости и прогнозы, быстрое обнаружение инцидентов и доказуемое улучшение SLA.

# Выбор подхода к мониторингу

Используем комбинированный подход (так надёжнее и прозрачнее):

* Четыре золотых сигнала (Latency, Traffic, Errors, Saturation) — для пользовательских API (Shop/CRM/MES, B2B-партнёры), чтобы иметь сквозное качество сервиса.
* RED (Rate, Errors, Duration) — для внутренних сервисов/консьюмеров очередей (Pricing, воркеры, интеграции), где «запрос = обработка сообщения/задачи».
* USE (Utilization, Saturation, Errors) — для инфраструктуры (RabbitMQ, БД, S3/хранилище, хосты/EC2), чтобы видеть ресурсные ограничения.

# Что меряем и как (метрики + зачем + ярлыки)

Ниже — нужные метрики из списка + добавленные. Для каждой: зачем и какие labels (ярлыки) добавляем. Все счётчики — монотонные; латентности — histogram (потом агрегируем p50/p95/p99). Где в списке есть «число 200/500» — берём одну метрику http_requests_total{status} вместо множества разрозненных.

## RabbitMQ (RED + USE)

1. Number of dead-letter-exchange letters (DLQ)

    * *Зачем:* индикатор потерь; триггер на инциденты.
    * *Ярлыки:* queue, vhost, message_type, environment, region, partner_id?.

2. Number of messages in flight (ready/unacked)

    * *Зачем:* бэклог и давление; ранний сигнал деградации.
    * *Ярлыки:* queue, vhost, environment, region.

3. Message rate (поступление/подтверждение) — добавляем

    * *Зачем:* баланс приток/обработка; расчёт пропускной способности.
    * *Ярлыки:* queue, message_type, consumer_group.

4. Consumer lag / age of oldest message — добавляем

    * *Зачем:* как долго сообщения ждут обработки (SLO breach).
    * *Ярлыки:* queue.

## API-шлюзы и бэкенды (Золотые сигналы)

5. Number of requests (RPS) — Shop/CRM/MES API

    * *Зачем:* трафик и ёмкость; триггеры автоскейлинга.
    * *Ярлыки:* service (shop|crm|mes), endpoint (шаблон), method, status, environment, version, partner_id (для B2B).

6. Number of requests (RPS) per user (или per partner для B2B)

    * *Зачем:* защита/квоты; выявление «шумных» потребителей.
    * *Ярлыки:* service, partner_id|user_id, endpoint, status.

7. Response time (latency) — гистограмма

    * *Зачем:* SLO p95/p99; деградации под пиками.
    * *Ярлыки:* service, endpoint, method, environment, version, partner_id?.

8. HTTP requests total (с разбивкой по коду)

    * *Зачем:* вместо отдельных «200/500»; рассчитываем error-rate.
    * *Ярлыки:* service, status, endpoint, method, environment, partner_id?.

9. Simultaneous sessions / active connections (Shop/CRM/MES)

    * *Зачем:* нагрузка на state/session store, планирование масштабирования.
    * *Ярлыки:* service, environment.

10. KB transferred in/out (ingress/egress)

* *Зачем:* стоимость трафика, «тяжёлые» эндпоинты/файлы.
* *Ярлыки:* service, endpoint, partner_id?, direction (in|out).

## Pricing Service (RED)

11. pricing\_jobs\_total{status} (queued|processing|succeeded|failed|timeout|canceled) — добавляем

* *Зачем:* поток задач и отказов.
* *Ярлыки:* model_hash, source (shop|api\_partner), partner_id?, complexity_bucket (по полигонам), environment.

12. pricing\_job\_duration\_seconds — histogram — добавляем

* *Зачем:* p95/p99 времени котировки для SLO.
* *Ярлыки:* source, partner_id?, complexity_bucket.

13. pricing\_queue\_depth / oldest\_job\_age — добавляем

* *Зачем:* давление/отставание.
* *Ярлыки:* queue.

14. pricing\_cache\_hit\_ratio — добавляем

* *Зачем:* эффект кэширования повторных моделей.
* *Ярлыки:* source, partner_id?.

15. 3D input stats: polygons\_count, file\_size\_bytes — histogram — добавляем

* *Зачем:* корреляция сложности и времени; обоснование лимитов.
* *Ярлыки:* source, partner_id?.

## Базы данных (USE)

16. CPU % for shop/CRM/MES API *(из списка)* — ОК, но важнее для хостов; оставляем.

* *Зачем:* утечки/пики.
* *Ярлыки:* service, instance, environment.

17. Memory Utilisation for shop/CRM/MES API & db instances *(из списка)* — ОК

* *Зачем:* давление GC/кэшей/буферов.
* *Ярлыки:* service|db, instance, environment.

18. DB connections (shop, MES) *(из списка)*

* *Зачем:* пул/утечки; пределы pgbouncer.
* *Ярлыки:* db_role (primary|replica), database, environment.

19. DB latency/slow queries count — добавляем

* *Зачем:* корень медленной MES-страницы.
* *Ярлыки:* query_fingerprint, database, environment.

20. DB locks/deadlocks/wait time — добавляем

* *Зачем:* конкуренция за таблицы заказов/статусов.
* *Ярлыки:* lock_type, relation, database.

21. Size of shop/MES db instance *(из списка)*

* *Зачем:* планирование хранения/индексов.
* *Ярлыки:* database, tablespace.

## Хранилище

22. Size of S3 storage *(из списка)*

* *Зачем:* бюджет/ретеншн 3D-файлов.
* *Ярлыки:* bucket, environment.

23. S3 request rate / 4xx/5xx — добавляем

* *Зачем:* лимиты/ошибки доступа к моделям.
* *Ярлыки:* bucket, operation (GET|PUT), status.

## Фронтенд/RUM (Shop/MES/CRM)

24. Web Vitals (LCP, FID, CLS), SPA route change latency — добавляем

* *Зачем:* UX операторов на главной странице MES.
* *Ярлыки:* app (shop|crm|mes), route, environment, browser.

25. WebSocket connections (MES operators) — добавляем

* *Зачем:* push-канал и его стабильность.
* *Ярлыки:* app, instance.

## Бизнес-метрики

26. Order funnel counts: submitted → price_calculated → manufacturing_started → shipped → closed

* *Зачем:* быстро видеть, где «течёт».
* *Ярлыки:* source (b2c|b2b), partner_id, country, sku_type (custom|catalog), complexity_bucket.

27. Lead time per stage — histogram

* *Зачем:* SLA по этапам, узкие места.
* *Ярлыки:* stage, source, partner_id.

28. Stuck orders gauge (в состоянии дольше SLA)

* *Зачем:* прямой триггер эскалаций.
* *Ярлыки:* stage, source, partner_id.

## «Железо» и сеть (USE)

29. Node/instance CPU, memory, disk IO, net IO, file descriptors — добавляем

* *Зачем:* фоновая ресурсная картина и saturations.
* *Ярлыки:* role (api|db|mq|worker), instance, environment.

# Алёртинги и SLO 

* SLO 1: p95 POST /pricing (асинхронный submit) ≤ 2s (приём запроса) и p95 pricing_job_duration ≤ 5 мин (тяжелые ≤15 мин).
  Алерты: burn-rate по error-rate > 2% (5xx/timeout) M-of-N окнами.
* SLO 2: p95 «SUBMITTED → CRM заказ создан» ≤ 30 сек.
  Алерты: oldest_message_age{queue=order_created} > 60 сек.
* SLO 3: Главная страница MES: серверная latency p95 ≤ 300 мс; RUM LCP ≤ 2.5 c.
  Алерты: p95 > целевого 10 мин подряд.
* DB: connections > 80% лимита, deadlocks > 0 за 5 мин — alert.

# План действий

1. Стек наблюдаемости

    * Развернуть Prometheus + Grafana (managed или в Yandex Cloud), Loki (логи), Tempo/Jaeger (трейсы), Alertmanager.
    * Принять стандарт OpenTelemetry (трейсы/метрики/логи коррелируемые).

2. Экспортеры и интеграции

    * Поднять RabbitMQ exporter; завести дашборды очередей, возраст сообщений.
    * Для Java сервисов (Shop/CRM): Micrometer + OTel; для C# (MES): OpenTelemetry .NET; включить http\_server/client metrics, гистограммы.
    * Postgres exporter: коннекты, блокировки, slow queries; включить pg\_stat\_statements.
    * S3/Yandex Object Storage: метрики бакетов через облачный мониторинг (запросы, байты, ошибки).

3. RUM и фронт

    * Внедрить лёгкий RUM-агент (безопасный, GDPR) в Shop/CRM/MES: LCP/FID/CLS, route-time, ошибки JS.
    * Счётчики WebSocket подключений в MES.

4. Сервисные метрики

    * Ввести единый формат метрик: service, environment, version, endpoint (шаблон), partner_id (только для B2B), не плодить высокую кардинальность.
    * Для Pricing: метрики задач (статусы, длительность, глубина очереди), polygons_count buckets, cache\_hit\_ratio.

5. Сквозные бизнес-метрики

    * События статусов (outbox) складывать в топик «analytics-events» → джобой агрегировать в time-series (Prometheus recording rules) + витрину в Grafana: воронка, lead time, stuck.
    * Настроить ежедневные отчёты и бенчмарки p95/p99.

6. Алёрты и онколл

    * Завести SLO дашборды и алёрт-политику (мульти-окно burn-rate, приоритеты P1–P3).
    * Интеграция Alertmanager с чатом/почтой/телефоном.

7. CI/CD-хуки

    * Автоматически прокидывать version, git_sha в метрики.
    * Синтетические пробы (blackbox exporter) для критичных эндпоинтов.

8. Документация и обучение

    * Плейбуки инцидентов, гайд по чтению дашбордов, лимиты на ярлыки, общие имена метрик.

9. Безопасность и cost control

    * Retention политики (метрики 30–90 дней, логи 7–14 дней), сэмплинг трейсов (tail-based на ошибках/медленных).

---

Если кратко: ставим «скелет» — Prometheus/Grafana/OTel + экспортеры (RabbitMQ/DB/Node) и стандартизируем метрики API по золотым сигналам; для очередей и воркеров — RED; для БД/инстансов — USE. Добавляем бизнес-метрики воронки и времена стадий. Это даст прозрачность «где теряются заказы» и куда вкладывать усилия, чтобы вернуть SLA и клиентов.
